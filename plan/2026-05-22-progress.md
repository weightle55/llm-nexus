## 1. 요약

`shell_exec` 도구를 도입하면서 "에이전트가 시스템 명령을 사람의 승인 없이 실행할 수 없게 하는" 안전장치를 백엔드에 구현. 흐름은 `/chat` 이 승인 필요한 호출을 만나면 즉시 `pending_approval` 로 응답하고, 사람이 `/approvals/{id}/decide` 로 결정한 뒤 `/chat/resume` 으로 재개하는 **pending → decide → resume** 패턴. SSE(Phase 6) 와 자연스럽게 이어지도록 HTTP 를 길게 잡는 모델은 의도적으로 피함.

## 2. 신규 / 변경

### 신규 파일
- `backend/app/tools/shell.py` — `shell_exec(command, cwd, timeout)`. `subprocess.run(shell=True)` 로 실제 실행. stdout/stderr 4 KB 상한, 30 초 기본 타임아웃, `TimeoutExpired` → `{"error":"timeout"}` 으로 직렬화. 에이전트 루프는 직접 호출하지 않음 (승인 후에만 호출)
- `backend/app/routes/approvals.py` — `GET /approvals` (status 필터 기본값 `pending`, 옵션 `session_id`), `POST /approvals/{id}/decide` (body `{decision: "approve"|"deny", reason?}`). 이미 결정된 approval 재결정 시 400

### 변경
- `backend/app/models.py` — `Approval` ORM 추가. 컬럼: `id`, `session_id` (FK CASCADE), `tool_name`, `tool_call_id` (OpenAI tool_call id, resume 시 매칭용), `arguments` (JSONB), `status` (`pending|approved|denied`), `decision_reason`, `created_at`, `decided_at`
- `backend/app/tools/registry.py` — `APPROVAL_REQUIRED = {"shell_exec"}` set, `TOOLS` 에 `shell_exec` 스키마, `DISPATCH` 에 매핑. `call_tool()` 시그니처는 그대로 유지 — 호출 시점에 이미 승인됐다고 가정하므로
- `backend/app/agent.py` — 대규모 리팩토링:
  - 핵심 LLM 루프를 `_loop(db, session_id, convo)` 로 추출 (run_turn / resume_turn 양쪽에서 재사용)
  - `_execute_or_defer(db, session_id, tc, convo)` — tool_call 하나를 자동 실행하거나 `Approval(status=pending)` 로 큐잉. deferred 면 True 반환
  - 한 어시스턴트 응답에 자동/승인 도구가 섞여 있으면 자동은 즉시 실행해서 tool message 적재, 승인 도구는 pending 으로 큐잉. 그 사이클에 하나라도 deferred 가 있으면 LLM 재호출 없이 `pending_approval` 로 즉시 return → 사용자 결정 대기
  - `run_turn` — 진입 시 세션에 미해결 pending 이 있으면 새 메시지를 받지 않고 `pending_approval` 그대로 돌려줌 (정합성)
  - `resume_turn` — 마지막 어시스턴트 메시지의 `tool_calls` 를 순회하면서 아직 응답 안 만들어진 `tool_call_id` 에 대해 approval 결과대로 실행하거나 `{"error":"denied by user", ...}` tool message 를 적재 → convo 다시 로드 → `_loop` 재진입
  - `decide_approval(db, approval_id, decision, reason)` — approvals 라우터가 호출. status 전이 + `decided_at = utcnow` + commit
- `backend/app/routes/chat.py` — `ChatOut` 을 union 응답으로 확장: `status` 필드 (`ok|pending_approval|stopped`), 그에 따라 `reply` 또는 `approvals` 채움. `POST /chat/resume` 신규 (body `{session_id}`)
- `backend/app/main.py` — `approvals` 라우터 include

## 3. 검증 시나리오 (수동, end-to-end)

llama-server (네이티브, `owned_by: llamacpp`, `gemma-4-e4b-it-UD-Q4_K_XL.gguf`) + Postgres (Docker) 띄운 상태에서:

1. **Approve 흐름** — `POST /chat {message: "Run the shell command 'echo hello from approval' ..."}` → `{status: "pending_approval", approvals: [...]}` 응답. `GET /approvals` 에서 동일 row 확인. `POST /approvals/{id}/decide {decision:"approve"}` → status=approved. `POST /chat/resume` → `{status:"ok", reply:"The command printed \"hello from approval\"."}`
2. **Deny 흐름** — 새 세션에서 `"Run 'whoami' in the shell."` → pending. `POST /approvals/{id}/decide {decision:"deny", reason:"too risky"}` → status=denied. `POST /chat/resume` → `{status:"ok", reply:"I was unable to run the 'whoami' command because it was denied due to being too risky."}` (LLM 이 거부 사유를 그대로 자연어에 반영)
3. **Audit 적재** — `audit_log` 에 `approval_requested` (2건), `tool_call` (승인 후 실제 실행, 1건), `approval_denied` (1건, payload 에 reason 포함) 모두 기록됨
4. **회귀 없음** — fs_read / fs_write / fs_list 는 그대로 즉시 실행 (승인 안 거침)

## 4. 설계 결정

- **승인 대기 모델: pending 즉시 반환 + resume 패턴** — HTTP 를 길게 잡는 (asyncio.Event) 모델 대비 트레이드오프:
  - 장점: HTTP 타임아웃 무관. agent 상태가 DB 에 직렬화돼서 서버 재기동 시에도 복구 가능. Phase 6 SSE 도입 시 이벤트 모델이 그대로 맞아 들어감
  - 단점: resume 시 convo 를 DB 에서 다시 로드 (이미 fs_* 검증에서 쓰고 있던 패턴이라 코드 재사용)
- **자동/승인 혼합 응답 처리** — 한 어시스턴트 응답에 fs_write + shell_exec 가 같이 오면? 자동은 즉시 실행해서 tool message 적재, 승인은 pending 으로만 두고 즉시 `pending_approval` 반환. resume 시 pending 한 것만 처리. LLM 측에서 봤을 때 tool_call 의 응답 순서나 누락 이슈 없이 깔끔
- **재결정 차단** — 이미 결정된 approval 에 재호출 시 400. UX 상 deny 번복 같은 건 새 turn 으로 처리해야 함
- **`Approval.tool_call_id`** 를 인덱스 컬럼으로 — resume 시 `(session_id, tool_call_id)` 로 빠르게 조인하기 위해

## 8. 메모 / 결정 보류

- **타임아웃 정책** — 현재 30 초 / 4 KB 상한 하드코딩. 화이트리스트 도입 시 명령별 타임아웃 차등 가능
- **승인 만료** — pending 이 영원히 남는 케이스 (사용자가 결정 안 함). 향후 TTL 도입 검토 — 현재는 무한 대기
- **재결정 UX** — 현재 deny 번복은 새 사용자 메시지로만 가능. 어드민 UI 에서 "다시 시도" 버튼이 필요해지면 별도 엔드포인트 고려
- **shell_exec 작업 디렉토리 기본값** — 현재 `cwd=None` 이면 프로세스 cwd. 워크스페이스로 강제할지 검토 (보안 vs 유연성)
