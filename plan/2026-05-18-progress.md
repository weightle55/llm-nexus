## 3. Phase 4 — Agent 루프 + fs 도구

### 의존성
- `openai>=1.50` (llama-server의 OpenAI 호환 엔드포인트 호출용)

### 신규 파일
- `backend/app/llm.py` — `AsyncOpenAI(base_url=settings.llama_base_url)` 클라이언트, `chat()` 헬퍼. 모든 요청에 `extra_body={"chat_template_kwargs": {"enable_thinking": False}}` 자동 첨부 (아래 함정 ② 참고)
- `backend/app/tools/fs.py` — `_resolve_inside_workspace()`로 모든 경로를 `WORKSPACE_DIR` 안으로 강제. `fs_read`, `fs_write`(부모 디렉토리 자동 생성), `fs_list`. 탈출 시 `WorkspaceError`
- `backend/app/tools/registry.py` — OpenAI `tools` 스키마 + `DISPATCH` 매핑. `call_tool(name, args_json) -> str` 동기 디스패처 (JSON 인코딩된 결과 반환, 예외는 `{"error": ...}`로 포장)
- `backend/app/agent.py` — `run_turn(db, session_id, text)` 루프. 최대 `MAX_TOOL_ITERATIONS=8`회. 시작 시 `_load_history()`로 이전 메시지를 1회만 읽어 in-memory `convo` 리스트로 변환한 뒤, 매 반복마다 LLM 호출 → `tool_calls`면 실행+audit_log+tool 메시지 적재 후 `convo`에 append, 아니면 어시스턴트 메시지 적재 후 종료. LLM 입력 순서는 우리가 만든 리스트 순서로 보장됨 (DB `created_at` 정렬에 의존하지 않음)
- `backend/app/routes/sessions.py` — `POST /sessions`, `GET /sessions`, `GET /sessions/{id}/messages`
- `backend/app/routes/chat.py` — `POST /chat` (body: `session_id`, `message`)

### 변경
- `backend/app/main.py` — `sessions`, `chat` 라우터 include
- `backend/app/models.py` — `created_at`/`updated_at` 컬럼을 `DateTime(timezone=True)` + Python `default=_utcnow` 로 명시 (아래 함정 ③)

### 검증 시나리오
1. **단발 쓰기** — "Create hello.txt with 'hi from phase 4'" → 한 번의 `fs_write` 호출, 파일 정확히 생성됨
2. **다단계 추론** — "List the workspace, then read hello.txt and tell me its contents" → `fs_list` → `fs_read` → 두 결과를 종합한 한 문장 응답
3. **샌드박스 경계** — 직접 `call_tool("fs_read", '{"path": "../../.env"}')` 호출 시 `{"error": "path '../../.env' escapes workspace root ..."}` 로 반환. `/etc/passwd` 같은 절대 경로도 동일하게 차단

### 막바지 정리 (코드 polish)
1. **`agent.py` 루프 구조 단순화** — 위에 적은 in-memory `convo` 방식으로 전환. 매 반복마다 `SELECT * FROM messages` 다시 하던 코드 제거. `_messages_to_openai` 리스트 헬퍼는 `_message_to_openai` (단일) + `_load_history` + `_serialize_tool_call` 로 분해
2. **`fs.py` 반환 경로 정규화** — `fs_write` 결과의 `path` 필드를 `str(WindowsPath)` (백슬래시) → `.as_posix()` (슬래시) 로. Windows/Linux 양쪽에서 LLM·프런트가 같은 형태를 보게 됨
3. **시스템 프롬프트 톤 보강** — "Keep responses concise" 만으로는 도구 실행 후 응답이 빈 문자열로 끝나는 케이스가 반복적으로 나옴. "After every tool result, always reply with a short confirmation sentence — never leave the final response empty." 추가로 해결

## 4. 도중 만난 함정 3개

### ① 모델 이름 미스매치
- 처음 `/chat` 호출 시 `404 model 'gemma-4-e4b-it-UD-Q4_K_XL.gguf' not found`
- 원인: 사용자가 "llamacpp" 라고 칭한 서버가 실제로는 **Ollama 0.24.0** 였음 (`/api/version` 호출로 확인). Ollama는 모델 이름이 `gemma4:e4b`였음
- 사용자가 진짜 llama-server 로 재기동한 뒤 그대로 `gemma-4-e4b-it-UD-Q4_K_XL.gguf` 가 동작
- 교훈: `:11434` 는 Ollama 기본 포트이기도 함. `/v1/models` 응답에 `owned_by: llamacpp` 가 있어도 항상 일치한다 보장 안 됨 → 의심되면 `/api/version` 으로 식별

### ② `enable_thinking` × `tools` 충돌
- 모델 이름 수정 후 새 에러: `400 Assistant response prefill is incompatible with enable_thinking.`
- llama-server 빌드가 Gemma 4 에 thinking 모드를 기본 ON 한 상태에서 `tools` 동시 전달 시, chat template 이 빈 어시스턴트 prefill 을 prepend 하려다 충돌
- 해결: `chat_template_kwargs.enable_thinking=false` 를 모든 호출에 추가. `openai` SDK 에서는 `extra_body` 키를 통해 전달

### ③ 타임스탬프 동률 → 메시지 정렬 무너짐
- 증상: 사용자 요청 1회에 LLM 이 `fs_write` 를 **2번** 호출. 두 호출의 인자가 완전히 동일
- 원인: `Message.created_at` 이 `server_default=func.now()` (Postgres `now()` == `transaction_timestamp()`) 라서 같은 트랜잭션의 모든 INSERT 가 동일한 타임스탬프. 정렬이 `(created_at, id)` 인데 `id` 는 랜덤 UUID → 순서가 `[tool_result, user, assistant_tool_call, ...]` 식으로 뒤섞임 → LLM 이 "도구가 아직 안 불렸다" 고 판단하고 다시 호출
- 해결: `Message.created_at` (+ `AuditLog.created_at`, `Session.created_at/updated_at`) 컬럼을 `DateTime(timezone=True)` 로 명시하고 Python 측 `default=lambda: datetime.now(timezone.utc)` 추가. 매 `db.flush()` 마다 실제 wall-clock 이 기록되어 순서 보존
- 부수 효과: 컬럼 타입 변경이 필요해서 기존 테이블 `DROP TABLE messages, audit_log, sessions CASCADE` 후 재기동 (lifespan 이 `create_all()` 재호출)

## 7. 메모 / 결정 보류 사항

- **시스템 프롬프트 톤**: 도구 실행 후 어시스턴트 응답이 빈 문자열로 끝나는 케이스 있음 (단발 쓰기 시). UX 측면에서 "한 줄 확인" 을 강제할지 검토 — 다만 다단계 시나리오에서는 자연스럽게 요약 응답이 나오므로 우선 그대로 둠
- **메시지 정렬 안전망**: 현재는 wall-clock 마이크로초 정밀도에 의존. 동일 마이크로초 INSERT 가 발생하면 UUID 보조 정렬이 무의미 → 향후 `seq` Identity 컬럼 추가 검토
- **`MAX_TOOL_ITERATIONS=8`**: 임계치 도달 시 `event_type=error` 로 audit, 사용자에게 "iteration limit reached" 어시스턴트 메시지 반환. 실측 후 조정
- **Alembic / 인증 / 화이트리스트** 는 여전히 보류 (`plan/plan.md` §9 그대로)
